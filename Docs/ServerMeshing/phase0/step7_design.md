## Rules (the step 2/3/5/6 rules all bind; see `step6_design.md` "Rules")
- C# 9 on the overlap of netstandard 2.1 and unity-4.8-api (no records, `init` or default interface members). Unity 6000.3, so `Rigidbody.linearDamping`/`linearVelocity` exist.
- XML docs on every public type and member, starting with its name; other comments minimal. Errors carry context (object id, type, connection, cell); nothing is swallowed; constructors throw `ArgumentOutOfRangeException`/`ArgumentNullException` naming the field.
- Log lines: one physical line, invariant culture, fixed formats, no braces, never the word "Exception" (messages go through `MeshStateSender.CleanForLog`). TestMap never names a Tests type. ## Decisions (made; report them)
1. **Wire.** All three are payload sizes: the int32 length field of the kit/sender record `[packed uint id][int32 len][payload]` (`MeshStatePacketWriter.cs:8-9`, BGNM:741-743). Framed on the wire a record is `PackedUIntSize(id) + 4 + payload` (59-63 B for 54; packed uint is 1 B to 240, 2 to 2287, 3 to 67823, 4 to 16777215, else 5, NetDataWriterExtension.cs:179-209); an upload is `[packed ushort 119][packed long ts][packed uint id][payload]` with no length (BGNM:581-588): 1 + 3..10 (a packed long is two zigzagged packed ints; a Unix-ms stamp takes 2 + up to 5) + 1..5 B of header. Acceptance measures payload and framed sizes.
   - **legacy54** = the space game's exact `ShipMovementComponent` record (SMC:329-344): position 3 floats, rotation 4 raw floats x,y,z,w, linear velocity 3 floats, angular velocity 3 floats, movement state `PutPackedUInt` (0 None or 1 Forward, one byte), teleport byte (server→client the teleport sequence, client→server the acknowledged one). 54 B constant. Reason: it is the only format in the space code (space.md §2).
   - **header56** = 2-byte header + the 54: byte 0 = authority (bits 0-1) | flightState (bits 2-4) << 2, bits 5-7 zero; byte 1 = epoch. Reason: the space team's agreed reply-2 header; the bit order is ours until they confirm (question S2).
   - **compact28** = a rig-only 28 B layout, kept at 28 per critique 18: byte 0 = authority | flightState << 2 | forward << 5 | 1 << 7 (bit 7 is the compact indicator, choice **(A)**, rig-only until the team decides); byte 1 epoch; position 3 × signed 24-bit centimetres (±83,886.07 m; out of range → `WriteCompact28` returns false and the sender sends Full); rotation smallest-three in 4 B (2-bit index of the largest component, 3 × 10-bit components of the others in ±1/√2, sign normalised so the largest is positive); velocity 3 × int16 at 0.02 m/s (±655.34, clamped); angular velocity 3 × int16 at 0.001 rad/s (±32.767, clamped); teleport byte. 2+9+4+6+6+1 = 28. Our record of the space team's reply says "~26 B" (memory `space-mmo-use-case.md`): question S1. Compact is a far-observer encoding only: never uploaded, never reliable.
   Superseded on 2026-10-04 by step7b_design.md (space code c2eb4154).
2. **Sender integration.** The ship's movement component registers itself through `IMeshStateRegistry` and its kit-facing `WriteServerState` returns false while registered (the `SentBySender` pattern, `MeshKinematicCharacterBody.cs:90-95, 319-329`). Ships are never wrapped: the wrap queue refuses a slot handler that is a state source (`MeshKitWrapQueue.cs:261-262`), and skips silently an id already registered (`:225-226`). The retry, exactly:
   - on the server, at `OnIdentityInitialize`, it caches `GetComponent<MeshStateSender>()` on the manager's GameObject once. None there (MESH_SENDER unset or off: `InstallStateSender` adds nothing, `MeshMapNetworkManager.cs:109-123`) means it never registers and never polls again, so the default-off path costs nothing;
   - otherwise each server frame it reads only `IsSending` (`MeshStateSender.cs:89`) and calls nothing while it is false (so `Register`'s "not sending" refusal is never logged for ships; measure mode simply polls a bool forever);
   - the first frame `IsSending` is true it calls `Register(this)` once: true sets SentBySender; false (sources exclude direct, or the fan-out refused it, both logged once by the sender) stops the retry for good. `OnSenderReleased` stops it too (decision 2b); a `PuppetHeld` ship never registers.
   - **2b. One game-neutral Mesh/ hook:** `public interface IMeshSenderOwnedSource : IMeshStateSource { void OnSenderReleased(); }` in `Mesh/Sync/MeshSyncContracts.cs`. The sender calls it whenever IT lets go of a direct source without being asked: server stop (`MeshStateSender.cs:499-501`), object destroyed (`:619-620`), fan-out drop with no queue (`:640-641`) and the queue's drop callback (`MeshKitWrapQueue.cs:173-177`). Those four `is MeshKinematicCharacterBody` checks become `is IMeshSenderOwnedSource`. `MeshKinematicCharacterBody` implements it as `public void OnSenderReleased() => SentBySender = false;`, so its behaviour is byte-identical. `OnSenderReleased` must only clear the source's own state and never call back into the registry: `OnStopServer` calls it inside a `foreach` over `_direct.Values` (`MeshStateSender.cs:499-501`), so a re-entrant `Unregister` would throw there. An explicit `Unregister` does not call it (the caller clears its own state, as Puppets does, `MeshMapNetworkManager_Puppets.cs:204-208`). Reason: Mesh/ cannot name a TestMap type, and without the hook a dropped ship keeps returning false to the kit and goes silent (addon.md gap 4). New §0.15 Mesh/ name; a delivery-note line in SETUP §7.
3. **Record sizes.** A new pure `Mesh/MeshRecordSizeCounts.cs` walks the 119 records the meter already reads; `MeshSendMeter` holds one (created only when enabled) and its Send window prints an optional ` | sizes ...` group only when the new shipped key `MESH_METER_RECORD_SIZES=1` is set (default output byte-identical; the key is parsed only when the meter itself is installed, so junk with the meter off logs nothing). 4. **Engine terminal speed** uses the space engine's formula `(F/drag − F·dt)/mass` (ShipEngine:154-159): 125.33 m/s at mass 1, F 400, drag 3, dt 0.02 (50 Hz); 121.33 at the rig's default 0.03 step; boost 250.67. It is the steady state of PhysX damping `v ← (v + F/m·dt)(1 − drag·dt)` (force integrated before damping). Not F/drag (133.3, 6 % high), which is what force-after-damping would give: acceptance 5's patrol p50 tells the two apart in the real engine (1.504 against 1.600 m/s at scale 0.03).
   Superseded on 2026-10-04 by step7b_design.md (space code c2eb4154).
5. **Patrol** copies the space AI: orbit the spawn point at 400 m×scale, 0.05 rad/s, throttle 0.4 (≈ 50.13×scale m/s at 50 Hz). The **stay-in-rectangle priority is a rig-only addition** (cells need bounded ships; the space AI has none, space.md §4): after avoidance, before combat, a ship outside the cell rectangle inset by 10 % (or predicted outside within 3 s) steers to the rectangle centre at flight altitude at throttle 0.7. AI spawn points are drawn inside the rectangle inset by 10 % plus `PatrolRadius` plus 10 m×scale, so a patrolling ship never meets the rectangle and Return fires only after combat drift (the space AI's patrol cost is kept as it is).
   Superseded on 2026-10-04 by step7b_design.md (space code c2eb4154).

15. **RPCs and sync fields.** `[AllRpc]` goes ReliableOrdered on channel 0; the server walks **every** connection but sends only to those that subscribe to the object or own it (`HasSubscriberOrIsOwning`), re-serialising per receiver, and then runs the body on the dedicated server (`LiteNetLibRPC.cs:76-101`): `RpcFired`/`RpcImpact` bodies return at once when `IsServer && !IsClient`. So the RPC messages sent per call = the object's subscribers (plus its owner when not subscribed), and the per-call loop cost grows with all connections. Each call allocates (delegate, `object[]`, id string): `ServerMeshSyncLoad` logs bytes per RPC and gc0 instead of claiming gc0. Every RPC caller (sync load, combat) adds the expected sends at call time to an `rpcSends` counter (`Identity.CountSubscribers()`, plus 1 for an owner connection that is not a subscriber) so the Send window's RPC count can be checked. The shield `SyncFieldFloat` written every frame while recharging costs an O(dirty) `List.Contains` per changed write (LNGM.StateSyncing.cs:636-640), an unreliable delta per subscriber every tick (redundancy 3) and a 1 s reliable baseline: the Ships window counts shield writes; the D-dirty model in step 8 uses those terms.

18. **(added) Flight paths and the bot check.** Pathed ships (load `mirror` ships and ship phantoms) follow `ServerMeshShipFlightPath` in server time (`t = timestamp_ms / 1000`, double). 19. **(added) "Within 0.5 m×scale of the flight path" is distance to the path curve**, not to the scheduled point: the server mirror sets its transform on each upload and then chases a velocity-extrapolated target (SMC:163-178, 366-381), so a record lags along-track by up to ≈ v·50 ms (6 m at 125 m/s) while staying on the curve. The bot measures the distance from each record position to the path over path time [t − 0.25 s, t + 0.05 s] and reports the along-track lag separately. The distance is to the curve, not to the nearest of the scan's samples: 5 ms samples are 0.31 m apart at 62.5 m/s (scale 0.5), so a sample-only minimum would read up to 0.16 m for a point exactly on the curve (64 % of the scale-0.5 p99 budget); `DistanceToPath` therefore refines with the point-to-segment distance on the two chords next to the best sample (chord sag ≤ (v·0.005)²/(8·128) m×scale, negligible). Path shapes are kept gentle (semi-major 200-280 m×scale, axis ratio ≥ 0.8, so curvature radius ≥ 128 m×scale; the tangent-extrapolation offset is then ≤ 0.15 m×scale).
20. **(added) Load `mirror` ships** are server-owned ships in OwnerMirror authority fed in-process by `ServerMeshShipMirrorFeeder`: 20 Hz header56/legacy54 bytes from the flight path go through the ship's own `ReadClientStateAtServer` (the real decode, ack check and transform set, minus the transport). Phantom ships cost the real upload path. Reason: b5's mirror rows {100..800} need mirrors without that many phantoms; §0.15 already reserved the name.
21. **(added) Server-owned ships acknowledge their own teleports** once the logic tick (`Manager.LocalTick`) has advanced by 2 since `TeleportShip` (checked in the ship's Update, so `WriteState` stays state-free). That guarantees at least one full send pass carried the teleport reliably to every subscriber, as a client's ack one round trip later would; a plain "one frame later" ack could fall before the next 20 Hz tick at 30 fps and the teleport would never go reliably. Why not SMC:390's reliable-forever as the default: in the space game it hits only unowned ships that teleport, and its AI ships never do (Ship_AI has `respawnOnDeath` 0 and despawns, space.md §1); the rig's teleport respawn is itself a rig device for a constant ship count, so acking it keeps its cost at one reliable record per subscriber instead of inventing a permanent reliable stream the space AI never pays. Reported to the space team as S4 (sheet :1237).

## Risks
- The path-curve metric could hide an along-track timing bug: lag p50 is reported and must sit in 20-60 ms at scale 0.5; a value outside it is investigated before step 8.
- `EnterVehicle` is async with an enter-animation await (the seat itself is set before it): seating is checked the next frame, and a pilot never seated is logged; byte rows run without pilots (run 2).
- Load `mirror` ships are fed in-process (decision 20): rows built on them understate a mirror's receive cost; cost rows use phantom ships.
- At Play stop the kit destroys every object in one pass; a seated pilot's `EntityOnDestroy` exits its vehicle only while `IsServer` (BGE:256-263), and Unity's `Destroy` is deferred, so no destroy cascade is expected; any `Exception` line at stop fails the run and is chased then.
- The prefab's hash must never collide (the builder checks; a clash would silently replace the mount in `GuidToPrefabs`).
- A process that sees ship spawns without the registration (a bot without `-meshRigShips`) logs "is not registered" for each: accept scripts always pass `rig_ship_bot_args`; regress scenarios never set ship keys.
- Visible range at scale 0.03 is 60 m and the kit AOI updates every 1 s, so V per phantom depends on density; G1-S rows state V_move from the Phantom window.
- The O(AI × spawned) scan, server bolts with `RaycastAll`, the per-frame shield write and per-call RPC allocation are copied space costs, not rig defects; physics-query cost under scaling stays (E) (sheet :1263) until the dense scale-1.0 row.
- `MESH_METER_RECORD_SIZES` adds a record walk per 119 send; it is opt-in and never on overhead rows.
- Instance pooling: a reused ship that keeps a stale `SentBySender`, sequence or path would misbehave; `Clean` resets every field and a test covers the static helpers.
