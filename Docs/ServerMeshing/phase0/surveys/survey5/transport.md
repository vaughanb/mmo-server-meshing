# transport

## Summary
I read the kit's transport layer and every place the add-on touches it. Nothing was written or run.

**Verdict.** A wrapper transport that implements ITransport can be installed with no kit edits:
- ITransport and BaseTransportFactory are public, in the autoReferenced LiteNetLibManager asmdef. LiteNetLibTransport is sealed but has a public constructor.
- LiteNetLibManager.TransportFactory has a public setter (LiteNetLibManager.cs:42-48).
- The factory is read only lazily, in PrepareTransportFactory (:100-132). That runs from PrepareServerTransport inside StartServer (:214) and from PrepareClientTransport inside StartClient (:245). LiteNetLibManager has no Awake, and Start/InitTransportAndHandlers (:95-98, :150-157) never touch the factory.
- The map server's StartServer runs at least one frame after the game data loads: OnGameDataLoaded (MMOServerInstance.cs:810-824), then await UniTask.NextFrame (:831), then StartMapServer (:946-956).
- BaseInit-CE.unity is build scene 0 and holds the MeshMapNetworkManager. So at AfterSceneLoad, BaseGameNetworkManager.Singleton is set (BGNM:113) and IsServer is false. Swapping the factory there, or in MeshMapNetworkManager.Awake (:95-99), is safe.

**What the wrapper must forward.** All 18 members at ITransport.cs:8-25:
- six properties: ServerPeersCount, ServerMaxConnections, IsClientStarted, IsServerStarted, HasImplementedPing, IsReliableOnly;
- twelve methods: StartClient, ClientSend, ClientReceive, StopClient, StartServer, ServerSend, ServerReceive, ServerDisconnect, StopServer, Destroy, GetClientRtt, GetServerRtt.

The kit really uses ServerSend, ServerReceive, Start/StopServer, ServerDisconnect (LNGM:434, MMOServerUserHandlers.cs:59), Destroy (LiteNetLibManager.cs:138, 146), IsReliableOnly (LiteNetLibSyncField.cs:88 and :95), and the client members. It never calls GetServerRtt, GetClientRtt or HasImplementedPing; only MixTransport forwards them. The connect gate uses the inner transport's own counts (LiteNetLibTransportServerEventListener.cs:25, with `this` passed at LiteNetLibTransport.cs:98), so phantoms never take real connection slots.

**Precedent.** MixTransport.cs already composes two ITransports in the kit, draining one before the other in ServerReceive.

**Traps for the installation:**
1. When useWebSocket is true, PrepareTransportFactory replaces any factory that is not an IWebSocketTransportFactory (:113-123), and MMOServerInstance copies UseWebSocket onto the manager right before StartServer (:948). The wrapper would be dropped with no message, so this needs a check at server start.
2. The kit's fallback is GetComponent<BaseTransportFactory>() (:127). Once the metered factory is a component on the GameObject, that call can return the metered factory itself. Either way, the metered factory resolving its own Inner must skip itself. Calling the protected PrepareTransportFactory() from MeshMapNetworkManager reproduces the kit's choice exactly.
3. The same factory builds client transports too (:134-140). Bots run the same MeshMapNetworkManager prefab, so they get the wrapper on their ClientTransport. Build() runs on every StartServer and every StartClient.

**Chain semantics confirmed:**
- **Send:** LiteNetLibServer.SendMessage drops the bool that ServerSend returns (LiteNetLibServer.cs:114-117), so only the meter can see refused sends.
- **Receive:** LiteNetLibTransport.ServerReceive calls PollEvents on every call and dequeues one event (:104-114). LiteNetLibServer.Update loops on it (:49-57) and dispatches through OnServerReceive (:90-112):
  - connect: ConnectionIds.Add, then OnPeerConnected (BGNM:337-350, which kicks first when IsTemporarilyClose), then LNGM:437-442 creates the LiteNetLibPlayer;
  - data: TransportHandler.ReadPacket (:63-88) reads the packed ushort type, silently drops types with no handler, and catches handler errors;
  - disconnect: MeshMapNetworkManager:682, then MapNetworkManager:323-328 (async SaveAndDespawn), then BGNM:352-364, then LNGM:444-452.
- **peer.Send and the network thread:** NetPeer.Send (NetPeer.cs:45-46) leads to LiteNetPeer.SendInternal (:605-690), which copies the payload into a pooled packet and queues it. The logic thread runs every 15 ms (LiteNetManager.cs:113, 498-551). LiteNetPeer.Update (:1222-1320) merges queued packets into datagrams up to the MTU (SendUserData :1187-1213, SendMerged :1161-1185), then the socket sends them (LiteNetManager.Socket.cs:565-653).
- **Packed ushort:** 1 byte for 0-240, 2 bytes for 241-2287, 3 bytes for 2288-67823 (NetDataWriterExtension.cs:179-198). A ushort never uses the forms with a first byte of 250 or more. 65000 encodes as 249 244 248.
- **MTU:** fixed at 1024, because MtuDiscovery and MtuOverride are both off. The packet header is 1 byte for Unreliable and 4 bytes for channelled deliveries.
- **TooBigPacketException (LiteNetPeer.cs:640):** thrown for Unreliable above 1023 bytes, and for Sequenced or ReliableSequenced above 1020.

**Stale or wrong in the sheet:**
- line references: Ghosting.cs:164 is now :168; MeshMapNetworkManager_Load.cs:210 is now :259 (clients at :262);
- the TooBigPacketException condition is incomplete: Sequenced and ReliableSequenced throw too;
- 'the kit catches it' holds only on the path used when the grid is disabled;
- step 5 never says what the phantom factory's own inner transport is;
- TryReadMessageType takes no offset, so it cannot read the sink hello out of a NetPacketReader;
- the sink acceptance compares sink bytes with LiteNetLib BytesSent, which are different quantities;
- the regress path is wrong;
- for step 6: the contract file holds no IMeshStateTransport, so there is nothing to 'move out'.
