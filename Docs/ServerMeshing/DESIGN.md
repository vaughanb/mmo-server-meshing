# Grid-Based Seamless Server Meshing — Design

> Add-on for **MMORPG Kit Community Edition** (Unity). Goal: players cross
> cell/server boundaries with no portal disconnect, no loading screen, and
> (ultimately) the ability to see and fight across boundaries.

Origin (`MeshHandoff`, `inMemoryHandoffState` default on): sends it, warps the client, demotes the entity, then `SaveHandoffRowBehind` writes the row (a failure is logged; the destination's own periodic saves write the state, and the kit's updater proceeds every 5 s, so the behind-save lands first). Destination (`MeshMapNetworkManager_Ghosting`: `OnHandoffState`, `TryTakeHandoffState`; `DeserializeEnterGameData`): an enter-game whose user id and token match a state received within the reservation window is served from it by `ServeEnterGameFromHandoffState` — the kit's checks and registrations, minus the token validation (the origin vouched) and the row read — and the ghost is promoted as before; anything else takes the kit's database path. *Found on the way:* the state (mesh link) and the client's enter-game (its pre-connected transport) leave the origin in the same frame and the destination can poll the request first — six of the first run's ten hops fell back to the database that way; a request for a player whose ghost stands here now waits up to `handoffStateWaitSeconds` (0.15 s, one frame in practice) for the state. *Measured* (8 km demo, editor client, patrol x −15 ↔ 15 at z 512, ten hops a run): origin `Handoff SENT` server-side 6 ms (was 66), the row written behind the player in 89 ms; destination `enter-game served from the handoff state … in 0 ms` (was 133 ms of validate-and-load), or 33 ms when it waited the one frame for the state; the gap from the warp to the adoption 112–183 ms, median about 135 ms (was 250–360), the session's first hop 201 ms; every hop adopted, no fallback, no jump, longest frame 6.4–13.2 ms. | 1.03 | 2026-10-28 | **Pre-connect (the undetectable handoff, step 3): the client holds an idle connection to the cell it is approaching, and the hop takes it over.** *Why:* after 1.02 the longest frame of a hop was the connect frame, where the client transport was destroyed and rebuilt when the warp arrived, and the connect handshake was a round trip of the gap, which real latency multiplies. *Built:* server (`MeshMapNetworkManager_Preconnect.cs`): the boundary tick tells each owned player's client which neighbouring cell it is approaching — the nearest registered, linked neighbour within `preconnectDistance` (30 m) — with one `MeshPreconnectMessage` (id 1900) per change, an empty address once it leaves the band; forgotten on disconnect. Client (`ClientMigrationController`, "Pre-connect"): one warm connection built from the manager's transport factory, polled every frame, dropped on a disconnect, a 5 s timeout, a hint to another cell, a hop to another address, or the client stopping; a continuity hop to exactly its address takes it over. Core (CE-14): `LiteNetLibClient.AdoptConnectedTransport` and `LiteNetLibManager.MigrateClient(address, port, connectedTransport)` — the client continues on the warm transport (the holder consumed its connect event, so the manager raises its own) and enter-game goes out in the hop's frame. The per-hop line carries `preconnected=`; `PreconnectedHops` counts them. The destination sees an ordinary connected peer that has not entered the game (one `LiteNetLibPlayer`, kept alive by LiteNetLib's 1 s ping). The client's trace stamps during a hop are buffered and written once at its end: in the editor every log line captures a stack trace, and five of them sat in the enter-game frame. *Found on the way:* a hint that arrived while a hop still settled was dropped and, being sent once per change, never came again (half the hops of the first run connected cold); hints are taken at any time now. *Measured* (8 km demo, editor client, patrol x −15 ↔ 15 at z 512, ten hops a run, three runs): every hop `preconnected=True` once the dropped-hint bug was fixed; the warm connection connects 1–62 ms after the hint, seconds before the line; a steady hop's longest frame 5.1–8.5 ms against a 2.9–3.5 ms median, in no particular frame of the hop and with no garbage collection in it (the per-hop line now says `gcs N` and marks a GC in the longest frame); the session's first hop 12.6 ms, the hop's first-time code. **Hard rule:** implement by **extension and inheritance**, self-contained under `Assets/ServerMeshing/`
(namespace e.g. `MultiplayerARPG.MMO.Mesh`). **Do not edit existing core files** unless there is no
other option.

Unavoidable core edits must be (1) minimal — prefer adding a `protected virtual` hook; (2) marked
`// MESH-EDIT: CE-<n> — <reason>. See Docs/ServerMeshing/DESIGN.md §17`; (3) logged in
[§17](#17-core-edit-registry); (4) upstreamable where possible.

## 4. The core constraint

Seamless cross-border view is possible two ways: **(A)** client merges two server streams (worst fit
— singleton client, colliding ids, two scenes), or **(B)** the server ghosts neighbor entities into
the player's current cell over a server-to-server channel, keeping the single connection. **We build
(B).**

## 5. Target architecture

**Uniform grid cells + server-side ghosting + fast handoff.** *(Diagram and notes updated 2026-09-15,
0.50: no coordinator role — the world registry is static configuration every process loads.)*

```
        world registry (asset)  ─ one layout per map placed in a shared frame → cells, neighbours
        kit cluster (Central)   ─ cells are channels; addresses via the existing peer broadcast
        ┌──────────────┬───────────────────┬──────────────┐
        ▼              ▼                   ▼              ▼
   ┌─────────┐    ┌─────────┐         ┌─────────┐    ┌─────────┐
   │ Cell C  │≈≈≈≈│ Cell E  │≈≈≈≈≈≈≈≈≈│ Cell C2 │    │ Cell N  │   cells of one map share its frame;
   └────┬────┘    └─────────┘  seam   └─────────┘    └─────────┘   a seam between maps = a frame offset

   │  Client  │ ── seamless swap ──▶ (re-points to the neighbour behind stand-ins; at a seam the
   └──────────┘                        neighbour map's scene is pre-loaded and swapped in)
```

- Each cell = one map-server process running `MeshMapNetworkManager` (boundary tick, handoff, ghosting),

  same frame (§6).
- **No coordinator.** The registry gives every process the same cells, neighbours and frames; the kit's
  cluster gives the addresses; the central subclass lists the cells as channels; the login subclass
  routes by position. Ownership is by position (the owning cell of a rectangle) plus the handoff
  protocol for entities in flight. A coordinator only appears with dynamic cells (Q13).
- CellMeshLink streams border-band entity snapshots between neighbours (translated at a seam, §6).
- Ghosts = read-only replicas with authoritative behaviours disabled, spawned as normal identities.
- One simulator per entity; clients send input only to their authoritative cell.

## 6. World & coordinate model

*Rewritten 2026-09-15 (0.50) to the verified state after 0.46–0.49; the earlier text described per-cell
frames and the movement-grid limit, both of which turned out not to apply.*

- **Frames per map, not per cell.** A kit map (one scene) is one Unity frame at its own origin. The
  kit's quantized movement grid (`DefaultGridManagerComponent`, the source of the old ±960 m figure)
  is **disabled by default** with the kit's own note to re-enable it only after a rework, so the only
  limit on a map's size is float precision: at 5 km from the origin one float step is 0.5 mm. Target
  maps are up to **10 km × 10 km**, one scene each, no floating origin unless jitter shows up in a test.
- **The world registry** (`MeshWorldRegistry` asset, one `MeshMapLayout` per meshed map) places each
  map's scene origin in a **shared world frame** that exists only to compute adjacency: a uniform grid
  per map cuts it into **cells** (world rectangles), and two cells whose rectangles touch (edge or
  corner, `touchTolerance`) are **neighbours, whichever map each comes from**. Continents placed next
  to each other in the world join through their touching cells with no further data. Every cell of a
  map shares the map's frame (`frameOrigin` = the layout's `worldOrigin`).
- **A crossing inside a map changes nothing:** the frame offset between two cells of one map is
  zero. **A seam between two maps is a frame change and a map change in one hop.** Each cell link
  learns the sender's frame at hello (`sender.OffsetTo(receiver)`), and every position that arrives
  on a link is translated in the dispatcher before any handler sees it: ghost snapshots, hits, monster
  handoffs (pose and spawn position), building placements, the aim positions inside attack and skill
  replays. The handoff **save** is written in the destination cell's frame with the destination's
  map id, so a plain login on that cell agrees with it.
- **The band** is measured as the distance from a position to the neighbour's rectangle (Chebyshev),
  which equals the old shared-line / shared-corner rule on a uniform grid; a cell's neighbour list
  (up to 32, one bit each) replaces the fixed eight grid offsets. `B` is sized by Q1.
- **Full precision on the links.** Spike 0 showed the kit's client-facing movement encoding is lossy,
  so S2S transfers (handoff state, ghost positions) carry float positions in the sender's frame — never
  the compressed movement encoding. Clients keep the normal stream; ghosts use it like any entity.
- **The client at a seam** (0.48–0.49): while the player stands in the band of a neighbour of another
  map, that map's scene is loaded additively and moved to the frame offset, so the far side is visible
  before the line; at the hop the client swaps frames before the kit's scene-change handling runs (old
  scene unloaded, its runtime objects carried, the new scene at its natural origin). Without a
  pre-load the kit's normal scene load runs, with its loading screen, and the hop still completes.
- **Known limits of the pre-load:** a scene's light probes, reflection probes, static batching and
  occlusion data are bound to the scene's authored origin and do not move with its roots, so lighting
  in the pre-loaded strip can differ until the swap puts the scene at its natural origin. The rig's
  two maps share identical geometry, so their seam overlaps visually; real maps are authored to meet.

## 7. Authority model

```
┌─────────────────────────────────────────┐
│   border band (B)  ── ghosts in / out     │
│   ┌─────────────────────────────────┐     │
│   │   INNER region (authoritative)   │     │  ← this cell simulates
│   └─────────────────────────────────┘     │
│   handoff line = cell edge ± hysteresis H  │  ← ownership flips here, rarely
└─────────────────────────────────────────┘
```

- Inner region: fully simulated & owned here. Border band: overlap; ghosts exchanged both ways.
- Handoff line + hysteresis (`H < B`): ownership flips only once an entity is `H` m past the edge, so
  loitering on the line doesn't thrash.
- Invariant: **exactly one cell is authoritative for any entity.** Ownership follows position (the
  cell whose rectangle contains the entity, §6) and the handoff protocol for entities in flight; a
  ghost is never authoritative.

## 8. Global identity

The id used to track an entity across cells must be **stable across handoff, ghost↔real promotion,
and server restart.** A packed `(ownerCell << 32) | ObjectId` (v0.1–0.4) failed all three — owner
changes on handoff, `ObjectId` is per-process and reset on restart. Replaced with:

- **`MeshEntityId` — stable, owner-independent:**
  - **Players:** the persistent **character id** (already globally unique; survives everything).
  - **Server-spawned entities** (monsters, drops, harvestables, buildings): a **birth-provenance** id
    `{spawnCell}:{cellIncarnation}:{objectId}` that encodes *where it was born* (immutable) — never the
    *current* owner. `cellIncarnation` is a per-process value taken at start-up, so a restarted cell's
    ids never collide with the previous incarnation's (Q3; no allocator needed).
- **Per-cell mapping table:** every cell maintains `MeshEntityId ↔ local uint ObjectId` for each
  entity it holds (real or ghost).
- **ObjectId access (corrected):** the `ObjectId` getter is **public**, and
  `LiteNetLibAssets.NetworkSpawn(go, objectId, connectionId)` lets a cell **assign** a local
  `ObjectId` at spawn (`LiteNetLibAssets.cs:415-435`). So we can read and choose local ids; what the
  kit lacks is a *coordinated, stable, cross-cell* namespace — which `MeshEntityId` + the mapping
  table supply. (We never mutate an existing identity's `ObjectId`, so the `internal set` is a
  non-issue.)
- **Dedup / promotion:** a snapshot for `MeshEntityId X` is ignored if this cell already owns X as a
  real entity; otherwise spawn/update a ghost. On handoff-in, replace the ghost mapping with the real
  entity under the same `MeshEntityId`.
- Carry `MeshEntityId` on a `MeshIdentity : LiteNetLibBehaviour` (no edit to `LiteNetLibIdentity`).

## 9. Map-server routing: cells vs logical maps

*Rewritten 2026-09-15 (0.50): the plan below is implemented; no coordinator process exists.*

- **A cell is a channel.** A cell's map server registers with the kit's cluster under the kit's own key
  `{channelId}_{mapName}` with the cell id as the channel and the map id as the map name (e.g.
  `C_ServerMeshTestMap`, `C2_ServerMeshTestMap2`), so the peer registry and address broadcast work
  unchanged (Q11). `MeshCentralNetworkManager` appends every cell of the registry to the central's
  channel list (character selection and the per-channel connection limit accept listed channels only);
  `MeshMapSpawnNetworkManager` starts a meshed map once per cell through the kit's private
  `SpawnMap` (reflection; the kit's own loop would start every map on every channel) and leaves maps
  without a layout to the kit.
- **`currentMapName` stays the map id.** A cell's server resolves its own cell from its channel id
  and `-mapName` at start-up (`OwnCell`); a character's saved position resolves the owning cell.
  Crossing a seam changes the map id, as the kit's own map change would.
- **Login / character-enter:** `MeshLoginNetworkManager` rewrites the selected channel to the cell
  that owns the saved position, for any map that has a layout (a subclass on the login server; no core
  edit — CE-4 was not needed). A character saved on another cell is handed to the owner at its first
  boundary tick, which also covers a kit warp that lands on the wrong cell (not exercised by the harness).
- **Positions outside every grid** belong to the nearest cell of the map (clamped), so an unserved
  strip behaves as before.
- **Non-meshed maps** keep the classic single-map-server path untouched.

## 11. The seamless handoff

### Triggers

1. **Boundary tick (primary — walked crossings).** `WarpCharacter` is never called when a player runs
   across a cell edge (it's the explicit-teleport API: portals/items/NPC/GM/respawn). A walked
   crossing is just movement updates. So a **per-tick boundary check** (`MeshMapNetworkManager.MeshBoundaryTick`,
   every 0.1 s) compares each owned player's position to the cell edge ± `H` and begins the handoff.
2. **In-grid explicit warp (secondary).** *Planned, not built:* there is no `WarpCharacter` override. A kit warp
   that lands a character on the wrong cell is corrected by the destination's first boundary tick, which hands it
   off by position (§9).
   - **The game-facing form is contracted, not built** (2026-10-05, agreed with the space game): `IMeshHandoffService`
     in `Mesh/MeshHandoffContracts.cs` — `RequestHandoff(entityId, destinationId)` → ticket; `HandoffCompleted`
     (origin: Committed / Failed / RolledBack / Aborted) and `ArrivalCommitted` (destination, raised with the
     ok-ack). Nothing implements it yet; the service comes in the slice after Phase 0. Its timings are today's (ack
     guard 20 s, link-down grace 3 s, rollback hold 20 s, reservation 15 s, save retry 2 s).

### Sequence

1. **Pre-subscribe** — the crossing entity is already ghosted into the neighbor and the client already
   renders neighbor ghosts (why `B`/`H` budget for AOI latency, §6).
2. **State transfer** — *as built (the P1 baseline, decision 2026-09-12):* the origin unregisters the character and
   writes a full save (`WaitAndSaveCharacter`, State.All) at the crossing position in the destination's frame and with
   the destination's map id; the destination loads that row on enter-game and promotes its ghost in place. The DB is
   the transfer medium; the in-memory S2S transfer this step originally described was never built (CE-5 not needed:
   the relates data loads in the background instead).
3. **Ownership flip** at the line — the destination becomes the owner once it acks the notice; old cell demotes its real entity
   to a ghost; new cell promotes its received entity.
4. **Client transport migration** — re-point the client to the new cell. The kit's warp path already
   re-authenticates, resumes the character, sets ready, registers handlers, and binds ownership on the
   new map server. *As built since 1.01 (CE-14):* the client moves without stopping (`MigrateClient`); every
   entity it has is kept and the new cell's spawn of it adopts it, so the player's character, controller,
   camera, HUD and everything on screen carry on and object identity is preserved on the client (the ids
   change underneath). *Since 1.02* the adoption applies the new cell's initial state as a diff against what
   the kept object already holds (nothing fires for what did not change), a hop that stays in the active
   scene skips the kit's asset re-registration, and the hop's code is JIT-compiled at the first map load.
   *Since 1.03* the client pre-connects: the cell it is on names the neighbour it is approaching (within
   `preconnectDistance` of its edge), the client holds an idle connection to that cell, and the hop takes
   that connection over (`MigrateClient` with a connected transport) and enters the game at once — no
   transport rebuilt in the hop's frame, no connect round trip in the gap. Until 1.01 the client re-spawned behind stand-ins (the masked window, [SPIKE2.md](SPIKE2.md));
   that is now the fallback when the new cell does not seat us.
5. **Persistence** — new cell becomes owner-of-record; besides the save each crossing makes (step 2), saves are
   periodic + on logout.

## 12. Cross-border interaction (Phase 3)

- **Resolution rule:** the **acting** entity's owner resolves the action and sends an authoritative
  result to the **target's** owner over CellMeshLink, which applies it. Ghosts are never trusted for
  hit detection.
  *Implemented 2026-09-12 with one refinement:* the acting cell does the **hit detection** (against the
  ghost's colliders) and forwards the **raw attacker damage** (the kit computes defence/crit/miss at the
  target); the **target's owner** resolves it with the kit's `ApplyDamage` and reports the outcome back.
  Ghosts are invincible locally, so nothing is applied twice and no loot/exp is duplicated.
- **Projectiles/skills** crossing the seam are handed off like players, or resolved by their owner
  against translated ghost positions.
- **Lag comp across cells** needs neighbor history → ship recent transform history with ghost
  snapshots. **Snapshot rate is a real bandwidth/CPU knob** — tunable per entity class.
- **Ghost colliders/navmesh:** cross-border hits require ghosts to carry colliders — entangled with
  *which* components survive suppression ([Q7](#18-open-questions)+[Q9](#18-open-questions)); central
  to whether P3 is possible. *Resolved 2026-09-12:* colliders survive, server drivers do not (Q7, Q9).
- **Monsters/NPCs** near a border are owned by one cell, ghosted to the other; aggro must treat
  ghosted players as targets, routing threat across the link.
  *Implemented 2026-09-12:* the kit's own aggro works against a player ghost unchanged (a ghost is a normal
  player entity with colliders on the player layer, `IsEnemy` holds), once the monster is **awake**: the kit
  skips a monster's AI update while it has zero network subscribers, so [CE-7](#17-core-edit-registry)
  makes that check a virtual and `MeshMonsterActivityComponent` also counts a nearby player ghost as a
  watcher. The monster's hits land on the ghost, are forwarded to the owner and applied to the real player
  (the same GhostHit path as player→ghost hits, in the other direction).
- **Kill credit:** the kit rewards whoever is in the monster's damage records — on the killing cell that
  is the attacker's **ghost**. `MeshGameplayRule` (add-on subclass of the demo rule, swapped in on the
  `GameInstance`) intercepts `RewardExp/RewardGold/RewardCurrencies` for ghosts and forwards the **raw**
  amounts plus multiplier/given-type/levels to the ghost's owner over CellMeshLink; the owner applies them
  through the same rule to the real character (real caches, guild, pk state; nothing scaled twice). If the
  owner link is down the reward is dropped, matching what the kit does for a player who logged out mid-kill.
  Party/guild share and quest counters *(implemented 2026-09-13)*: resolved on the killer's owner cell
  with the real character (`GhostKill` for quests; `OnGhostReward` mirrors the kit's guild and party
  sharing). Party members standing on a third cell still get nothing (open).
- **Loot** *(implemented 2026-09-13)*: drops near the line are ghosted like monsters and shown as puppet
  drops on the neighbour; a pickup on a puppet is forwarded to the owner, which validates it against the
  requester's ghost, removes the real drop and sends the items to the requester's cell for the real
  character's bag. See changelog 0.22.
- **Monster handoff by position** *(implemented 2026-09-12)*: ownership of a monster follows its position
  like a player's does (same hysteresis, plus a per-monster cooldown against ping-pong on the line). The
  handoff is **in place on both sides** — the owner turns its entity into the ghost, the neighbour turns its
  ghost into the entity — so it is invisible to clients. The kit's respawn is owned by the spawn area, so a
  lent monster keeps a record at its **home** cell; the borrower reports its death (`MonsterGone`) and the
  home area spawns the replacement; walking home reattaches the spawn area. Summoned monsters are never
  handed off (their summoner is a player, and they follow the player's handoff instead — open).

## 13. Persistence

- **One full save per crossing** (the handoff's transfer medium, §11 step 2), otherwise periodic + on logout + clean
  shutdown. **Owner-of-record:** exactly one cell may persist a character; it transfers atomically with the handoff.
- **Buildings (0.81, Slice 4):** the kit keeps buildings per channel and map; on a Dynamic map every cell of a split
  family persists them under the **base cell's channel** (CE-10, `BuildingPersistenceChannelId`), loads only the trees
  whose root stands in its owned rectangle, and only once the central has answered its layout. A tree's owner of record
  is the cell that owns its root's position: the holder force-saves every piece (and a chest's storage rows, keyed by
  the building's id, no channel) before it demotes its copies and sends the tree, and the receiver only reads, so a
  crash on either side mid-release loses nothing. A puppet's despawn never deletes a row (the kit deletes on every
  despawn; the add-on's override lets only an owned building through).
- **Crash / cell death mid-handoff (implemented 0.36, no coordinator needed):** the handoff's **commit
  point is the destination's ack** (the character registered there). Until then the origin still holds the
  character: the row it saved carries the origin's own channel (the kit's map-change save never writes a
  channel; only the destination's own saves move it), and the demoted puppet stands on the origin with its
  pets. If the destination dies, its link dies, or it stays silent past the guard, the origin **rolls the
  handoff back**: the puppet is held for the client's return instead of expiring stale. The **client falls
  back** to the cell it left when the destination refuses or never answers (the kit's disconnect handling
  is suspended during a hop), and the origin promotes the held puppet in place on its return — the same
  path as a normal arrival. A warp that reaches the client while a hop is still settling is queued, not
  dropped. If the destination acked and then dies, its own players are its problem (as with any dead kit
  map server) and its neighbours clean up: monsters it held for them respawn at home, monsters they held
  for it are dropped (its spawn areas respawn them when it returns), its ghosts expire stale, an arrival
  it announced is still served.
- **A cell that comes back:** the kit's MapSpawn restarts a dead map server within seconds, on a new port,
  but the cluster refuses the registration while the dead one is still in its peer table (`MAP_EXISTED`)
  and the kit never retries — the add-on retries every few seconds until accepted; the cluster then
  broadcasts the new address and the neighbours re-link. A restarted cell has no state: it receives its
  neighbours' ghost streams at once and promotes arrivals in place like any other cell.
- **Re-login after a cell died (0.41):** the login server now routes a character on the meshed map by its
  saved **position** — the cell whose zone owns it when that cell is registered with the cluster, otherwise
  the nearest live cell of the map, which serves the character where it stands and hands it off by position
  the moment the right cell is back. The client's chosen channel and the row's channel no longer matter on a
  meshed map (`MeshLoginNetworkManager`, an add-on subclass on the demo's server-instance prefab, rewrites the
  request's channel in front of the kit's own select-character handler). Maps outside the grid keep the
  kit's routing.

## 14. Risks

1. **Singleton client migration** (no scene reload **or** session/handler loss) — biggest risk, most
   likely core edit ([CE-1](#17-core-edit-registry)). **Spike 2 first.**
2. **Ghost simulation-suppression** — normal prefab runs server logic on spawn (AI/movement/regen/
   buffs); a ghost must neuter authoritative behaviours while keeping transform/visual/collider.
   Mechanism open ([Q9](#18-open-questions)); gates P2/P3.
3. **Coordinate/movement serialization across cells** — the byte-`cellId` quantized movement grid must
   correctly represent cell + band and translate ghost positions; mis-sizing clamps positions.
   **Spike 0.**
4. **Identity stability** — `MeshEntityId` must survive handoff/restart/promotion and dedupe cleanly.
5. **Routing integration** — login/enter must resolve position→cell; possible core touch (CE-4).
6. **Monster/projectile ownership at borders** — double-spawn / duplicate-damage.
7. **DB consistency** through handoff/crash (§13).
8. **AOI subscription latency (1 s)** — fast crossings outrun ghosting; mitigate via `B`/`H` + faster
   path (§6). *Sized and checked at start since 0.37 (Q1): 11 m of band buys the whole AOI pass at
   mount speed; the band is bound by the visible range, not by speed.*
9. **Partial failure** — a dead cell must fall back to the classic DB-warp path, not strand neighbors.
10. **Kit-update drift** — mitigated by no-core-edit policy + `MESH-EDIT` markers.

**Dynamic cells: what the plan leaves (known limits, 2026-10-20).** The operator's version, with the settings, is SETUP
§6a.12; the measurements behind each are in the changelog rows named.
- One operation runs at a time world-wide: the drain is paced to the database's sustained rate (0.75, 0.80).
- A cut relieves little for a crowd narrower than twice the band or standing on a base cell's edge; the kinematic cost
  model accepts a crowd narrower than the band that only a steered fit refuses; the weights are one machine's fits
  (0.71, 0.73, 0.80). Per-client downstream is unchanged.

  the ceiling of a map that keeps it; a map with `onDemandLinks` (0.86) links each cell only to its band neighbours and
  the cells it has business with, and is bounded by its hosts' port ranges (64 per host on the rig) instead. A cell
  streams to at most 32 band neighbours, and layout changes past it are refused (0.72, 0.83 warns before Play).
- A family runs on its base's host and never moves (0.90): while that host's spawner is away its splits are refused and
  its dead cells are not restarted; a host without a spawner cannot serve a Dynamic map's cells (MULTIHOST §6b); keep the
  hosts' clocks within 2 s (an on-demand link releases a restarted neighbour's records by its incarnation start). Sleeping
  cells have not been run across two hosts.
- The central's policy plans with the asset's `bandWidth` whatever `MESH_BAND` a run sets, and cuts only on the load
  report's bucket, so a base just over twice the minimum cell splits by command but never by the policy (0.83).
- Scene buildings and chests stay per-channel copies; `buildLimit` is per process; a building placed while its owner
  restarts has two owners for about a second; upstream 0008 (CE-10) is in OpenMMORPG `develop` since 2026-10-20 (d077c5f, [PR #8](https://github.com/open-mmorpg/OpenMMORPG/pull/8)), so the kit needs no hand edit (0.81, 0.84).
- `unfreeze` asserts that a frozen family's missing children are gone: one alive out of the central's sight keeps its
  rectangle beside the survivor until its next hello is fenced; a restart before the collapse's hand-over freezes the family
  again; a dead child sharing no full edge with a live cell is left down (0.85).
- After a central restart: a family whose child never says hello stays frozen until `unfreeze` (0.85); a store lost
  together with a partitioned cell can leave that cell holding an unadopted layout; the policy's multipliers and
  measurements and the supervisor's counts are forgotten and a resumed operation is not measured; a staged commit held
  by its target alone lasts the outage; a frozen operation is dropped; a central process hosting the database manager
  costs every cell up to 40 s of failed saves (0.82).

## 19. Glossary

| Term | Meaning |
|---|---|
| **Mesh cell** | One tile of the uniform world grid = one map-server process (coarse, *inter-server*) |
| **AOI grid** | Fine intra-server interest grid (`JobifiedGridSpatialPartitioningAOI`, cellSize 64) |
| **Movement grid** | Intra-server *position-compression* grid (`DefaultGridManagerComponent`, byte `cellId`, cellSize 128, `gridSize ≤ 15`) |
| **Logical global position** | `(meshCellId, localPosition)` — persisted/routed; Unity transform stays cell-local |
| **Border band (`B`)** / **Hysteresis (`H`)** | Overlap zone for ghosts / distance past edge before ownership flips (`H < B`) |
| **Boundary tick** | Per-tick check (`MeshMapNetworkManager.MeshBoundaryTick`) detecting walked crossings — the **primary** handoff trigger |
| **Ghost** | Read-only replica; authoritative behaviours suppressed; never simulated locally |
| **MeshEntityId** | Stable, owner-independent cross-cell id (character id for players; birth-provenance id otherwise) |
| **cellIncarnation** | Per-process value taken at a cell's start-up; keeps `MeshEntityId` unique across restarts |
| **Owner / owner-of-record** | The single cell that simulates an entity / may persist it |
| **Handoff** | Transfer of authority + client connection to a neighbor |
| **CellMeshLink** | Server-to-server channel between adjacent cells |
| **Mesh Coordinator** | *Dropped (0.50)* as a standalone role; static cells need none (registry + kit cluster + login routing). *Back (0.72-0.80) as the central's layout coordinator* for Dynamic maps: it owns the runtime layout, runs splits and merges, supervises the cells and, since 0.80, decides them from the cells' load reports |
| **ManagerComponent** | `BaseGameNetworkManagerComponent` — the kit's lifecycle-hook extension seam |
| **MESH-EDIT** | In-code marker for an unavoidable core edit, logged in [§17](#17-core-edit-registry) |
